Invariants to keep while changing these components:

- Note recovery (recovered copies never enter the editor or autosave automatically): Preserve that boundary when changing note identity, save sequencing or panel teardown.
- Single-event recovery: Never remove the frozen recovery compatibility when changing presentation.
- Stripped-parameter provenance: Provenance must never retain removed values or an extra raw URL.
- Containers: Downgrading after adding repositories is unsupported: older hosts reject `within` in the adapter config and in adapter history.
- Auto-summary: Deploy the host and the extension together: an older extension rejects a `config_result` that holds `auto_summary`, and an older host answers `start_auto_summary` with `invalid_request`. A `config.toml` whose auto-summary settings differ from the defaults holds `[auto_summary]`, which an older host refuses: delete it before a rollback. A rolled-back host also cannot read a newer run record's answer (`deny_unknown_fields`), so its run card shows no answer for those runs.
- Task bar: Roll back the service only with no task queued or running. An older build cannot read a task's `status.json` (`deny_unknown_fields`), so its recovery skips that record and cannot kill the task's process group, and old task records stay unreadable to it until they are pruned. Deploy the host and the extension together: an older extension rejects a `runs_listed` that holds a task view, and an older host answers `start_task` with `invalid_request`.

## Brauser is separate from AMOS

Brauser is its own product and its own project. Its repository sits inside the
ENDURANCE vault (`work/rauserBrowser`), but Brauser is not part of AMOS.

- **Standalone product.** DESIGN.md's principle 9 governs this repo: no file,
  build step, test, or default here may assume AMOS/ENDURANCE, Backstaff, or
  Astrolabe exist. Use [DESIGN.md](DESIGN.md) for intended behavior and update
  it when implementation changes a contract.
- **Work to John's standards, keep Brauser's things here.** Agents working on
  Brauser follow John's AMOS working standards (the ENDURANCE root `AGENTS.md`
  and its companions: validation, commit and deploy through the supported path,
  honest reporting, closeout, logging significant work in the weekly actions).
  This file adds the Brauser rules on top. Where the two disagree about a
  Brauser matter, such as where a Brauser artifact goes, this file wins.
- **Brauser artifacts live in this repo.** Its instructions, design,
  decisions, plans, backlog and improvement suggestions are files here. Do not
  write Brauser project content into AMOS artifacts (`AMOS_docs`,
  `AMOS/inventory`, the AMOS Improvement Feed, topics), and do not make a
  Brauser file point into the vault. `PENDING_AMOS_DOC_UPDATES.md` collects
  notes that an AMOS-side owner may choose to pick up; agents write it here and
  never push it into AMOS themselves.

### Brauser Improvement Feed

[BRAUSER_IMPROVEMENT_FEED.md](BRAUSER_IMPROVEMENT_FEED.md) is the entry point
for improvement suggestions about Brauser: the app, this repo, and how agents
build it. For Brauser work it replaces the AMOS Improvement Feed. Entries live
one per file in `docs/improvement-feed/`.

- Every substantive Brauser task produces one actionable suggestion: say it in
  chat and add it to the feed. Skip this only when John asked for exact
  output or no side effects.
- A suggestion about AMOS itself, not Brauser, still goes to the AMOS feed.
- Add an entry as a new file `docs/improvement-feed/YYYY-MM-DD-<slug>.md`
  (lowercase slug from the title; add `-2` if the name is taken). It starts
  with its own `## YYYY-MM-DD — Title` heading, then says what to change, why
  (the evidence from the task), and where (files or commands). Never rewrite
  another entry's text, and never add entries to `BRAUSER_IMPROVEMENT_FEED.md`
  itself.
- To reinforce an existing entry instead of repeating it, add a
  `- +1 YYYY-MM-DD: <new evidence>` line at the end of its file. When an entry
  is done, add `- Done YYYY-MM-DD: <PR, commit or bead>`.
- One file per entry means two PRs adding entries never conflict, even under
  GitHub's plain merge, which ignores `.gitattributes` merge drivers.
  `scripts/check_improvement_feed.py` (run by `scripts/check_current_state.py`
  in CI) checks the names and headings. The feed is under `docs/`, so a
  feed-only PR is docs-only in CI.

### Instruction files

Brauser has two kinds of instruction files. Keep them apart.

| Kind | Audience | Files |
|---|---|---|
| Project instructions | Contributors and the agents building Brauser | `AGENTS.md` (this file), `README.md`, `DESIGN.md`, `TESTING.md`, `adapter-templates.md`, `BOSUN_FEATURE_BACKLOG.md` (rendered from `docs/backlog/` and the beads, never committed; see "Work queue"), `worker-contract.json` (see "Worker contract"), plans and specs under `docs/` |
| App instructions | The agents Brauser itself runs for the user | `SUMMARY.md` (the page-summary agent's instructions, compiled into the host) |

- App instruction files are product code. They ship inside Brauser, are
  checked by tests, and run on any user's machine, so the standalone rule
  applies in full: nothing about John, AMOS, or the vault.
- Each app instruction file is the single source of truth for its agent's
  task. Change what that agent is told in the file, never in code.
- A new app instruction file goes at the repository root with an upper-case
  name, is compiled into the host, gets tests that fail on a malformed file,
  and is added to `BUILT_ROOT_MARKDOWN` in `scripts/ci-changes.mjs` so CI
  treats it as code.

Every other change (adapters, starters, the extension UI and worker, the protocol schema, cross-platform host code, scripts) is covered by Windows, and every push to main runs macOS too, so main's own run catches what a PR's skipped macOS build would have. Replayed on the last 45 code PRs (2026-11-03), macOS ran for 26 and was skipped for 19 (it used to run for all). Each skipped job writes why in the `Classify changes` log (`macos "<path>": <reason>`). The axe and keyboard checks (`npm run test:a11y`) run once, in the ubuntu `Accessibility` job, for every code change. `build-os.yml` can also be run by hand for one platform (`gh workflow run build-os.yml --ref <branch> -f os=macos-15-intel`), the way to prove the fallback passes, and `BRAUSER_REQUIRE_IPC_TESTS=1` so socket tests never skip. When GitHub cancels a starved `macos-15` job (cancelled with zero steps run, checked through the Actions API), the same steps rerun on `macos-15-intel` (x64; a separate runner pool from the arm64 images); a real failure, timeout or interruption of `macos-15` does not fall back. The `Build and check` gate job, the check branch protection requires, passes only when Windows and Accessibility pass and, when the change needs macOS, macOS passes on `macos-15` or, after that cancellation, on the `macos-15-intel` fallback (when it does not, macOS must have been skipped). A PR is compared from its merge commit to that commit's base parent, a merge group from its head to the queue's base commit; pushes to main always build. A new push to a PR cancels that PR's superseded CI run (whose cancelled macOS job never counts as starvation); runs on main are never cancelled. The Mergify merge queue (`.mergify.yml`, see "Review and merge cadence") tests a queued PR on a draft PR from a `mergify/merge-queue/<hex>` branch, so `ci.yml` and `pr-hygiene.yml` run there through ordinary `pull_request` events and the classification above compares main plus the PR with main; `PR owner` exempts those drafts. The `merge_group` triggers are unused (GitHub's own queue needs an organization-owned repository) and harmless.
- `.github/workflows/pr-hygiene.yml` runs cheap ubuntu process checks: the `PR owner` job (`scripts/pr-owner.mjs`, see "PR ownership and handoff") and the `Dev tools` job (`npm run test:dev-tools`, the Python tests for `scripts/dev/`). `.github/workflows/mergify-enqueue.yml` is a safety net that turns a GitHub auto-merge armed on a pending PR into the Mergify `queue` label. `.github/workflows/merge-hold.yml` is retired: it posts `merge-hold: success` on every PR head only because branch protection still requires that status; delete it once John removes the requirement.
- **PR doctor** (`.github/workflows/pr-doctor.yml`, `scripts/pr-doctor.mjs`; every 20 minutes, on every push to main, and by hand). A PR that conflicts with main runs no CI, so a queued PR waits forever with nothing failing. The doctor lists open same-repo PRs into main that GitHub reports as conflicting. It merges main into each one using main's `.gitattributes` and main's copies of `work_queue.py`, `render_backlog.py` and `check_queue_consistency.py`, never the PR's. It resolves only two kinds of conflict. One is an old PR that still edits `.beads/issues.jsonl` or `BOSUN_FEATURE_BACKLOG.md`, which left git ("Work queue"): it checks the PR's queue edits against the database and main's frame, drops both files on the PR side, merges main (exact renames only), then applies the bead edits through bd and syncs (`work_queue.py adopt`, in a database the workflow bootstraps from `refs/dolt/data`) and commits the PR's backlog prose into `docs/backlog/frame.md`; a queue edit that conflicts, or a workflow run without a database, is left to a person with instructions. The other is Markdown hunks where both sides only inserted text (a diff3 hunk with an empty base; main's text first). It pushes the merge without force and comments once on the PR (one sticky comment, updated in place, that mentions nobody). Any other conflict gets the `needs-merge` label and a comment listing the files; resolve those yourself, and the label clears on the next run. GitHub's own conflict check ignores the custom merge drivers, so a PR it calls conflicting can still merge cleanly here. Repairs are pushed only with the `PR_DOCTOR_TOKEN` secret (a fine-grained token with Contents and Pull requests write), because a push made with the workflow's `GITHUB_TOKEN` starts no CI; without it the doctor only reports. `scripts/dev/pr-watch.mjs` applies the wait-for-the-doctor rule for you. Opt a PR out with the `pr-doctor:skip` label (which also keeps it out of the Mergify queue). After a repair, pull before pushing again: your next push is rejected until you do.
- `TESTING.md` is this repo's own testing strategy (headless end-to-end recipe, dialog seams, what headless cannot prove). It is self-contained; nothing in this repo should point outside it for testing guidance.

## Local checks

## Worker contract

`worker-contract.json` at the repository root is the authority every worker follows: the shared worker driver (Cookie's), every session, and any automation that merges PRs or moves the queue. It is versioned and validated against `worker-contract.schema.json` (`scripts/tests/test_worker_contract.py`); a worker that does not understand its `version` must stop rather than guess. Where this file and the contract disagree, the contract wins and this file is the bug.

- **`merge`**: a worker asks for a merge by adding the `merge.label` label (`queue`, the Mergify merge queue's label; see "Review and merge cadence") to its PR and never runs a command in `merge.never` (`gh pr merge`, with or without `--auto`). After adding the label, the worker also posts `merge.comment` (`@Mergifyio queue`) as a PR comment: label-only auto-queue depends on Mergify's Merge Protections being activated in the dashboard, and the comment queues the PR either way. `scripts/dev/pr-watch.mjs` prints `gh pr comment <n> --body "@Mergifyio queue"` for a labeled PR stuck at "Merge queue is ready".
- **`queue`**: the work queue's transport is `bd-dolt` (below). A fresh clone runs `queue.bootstrap` once; after editing beads with bd, run `queue.sync`; `queue.export` prints the whole queue as JSONL on stdout; `queue.backlog` prints the rendered `BOSUN_FEATURE_BACKLOG.md`.
- **`queue.sync_exit_codes`**: what `scripts/dev/queue sync` exits with, for a worker to branch on. 0 `synced` (or nothing to do). 1 `error`: a failed queue check, a never-seeded remote, or a transport, auth or storage failure; nothing pushed; read the one-line reason. 2 `conflict`: bd sync halted on a merge conflict and pushed nothing; an operator resolves it (`bd conflicts`). 3 `retry`: a push race or another writer's pending edit; nothing pushed; sync again on the next tick. 4 `stuck`: the working set will not publish until an operator clears it (`bd sync --help`). 2, 3 and 4 are bd sync's own statuses, passed through unchanged.
- **`never_commit`**: no commit adds or changes these paths. `scripts/check_current_state.py`, which every CI path and `gate:adapter` run, fails a change that tracks either, and `.gitignore` lists them.

## Work queue

The queue is not a file in git. bd keeps the beads in its Dolt database and syncs them through this repository's `refs/dolt/data` (bd also maintains a `__dolt_remote_info__` branch there; leave both alone). `bd sync` merges concurrent edits field by field (the same bead edited in different fields keeps both) and halts, pushing nothing, on a conflict it cannot settle. Pull requests never carry the queue, so they never conflict on it. This replaced a committed `.beads/issues.jsonl` (2026-11-03), which PRs touched dozens of times a day and GitHub marked conflicting, running no CI.

- **Set up.** In a fresh clone, from the root: `BD_NON_INTERACTIVE=1 bd bootstrap` (it clones the database from `refs/dolt/data`). Linked worktrees use the main checkout's database.
- **Edit with bd, then sync.** Change beads only with bd (`bd update`, `bd close`, `bd dep`, `bd label`, or `scripts/dev/create-bead` for a new one), then `scripts/dev/queue sync`. Sync checks this database's queue, pulls, checks the merged queue, and only then runs `bd sync`; a failing check, or a remote that was never seeded, pushes nothing and says why. `bd sync`'s exit codes are passed on unchanged ("Worker contract", `queue.sync_exit_codes`). There is no file to edit, copy or export over the database.
- **Create.** `scripts/dev/create-bead "Title" -d "Description" --acceptance "Done when…" -t task -p 2` pulls first (so the id cannot collide with one created elsewhere), creates, and syncs. It refuses database or directory overrides.
- **The backlog view.** `BOSUN_FEATURE_BACKLOG.md` is rendered on demand and never committed: `scripts/dev/queue backlog` writes `target/queue/BOSUN_FEATURE_BACKLOG.md` (git-ignored), `--print` prints it. It is `docs/backlog/frame.md` (the hand-written preamble, section intros, Notes, older observations and Shipped history, with empty `<!-- BEGIN GENERATED section=… -->` blocks) plus every note under `docs/backlog/notes/` (one file per new cycle observation or handoff, so two branches never edit the same file), with each block filled from the beads by `scripts/render_backlog.py`. Edit the frame's prose or add a note in a normal PR; never write inside a GENERATED block. An open `- [ ]` item outside the blocks fails the check: open work is a bead.
- **Export.** `scripts/dev/queue export` prints the whole queue as JSONL on stdout (`bd export`); with a path it also writes it there. An empty queue fails, since a real queue never exports nothing. Readers take that output, never a committed file.
- **How workers run these.** The shared driver runs the contract's `queue` commands as given, from a pristine checkout of main (the cwd; its frame and tools are the ones used), with `BOSUN_WORKSPACE=<workspace>` and `BEADS_DIR=<workspace>/.beads` naming the database they act on, outside any sandbox, with no TTY, and with `GH_TOKEN` and a git credential helper in `GIT_CONFIG_*`. bd runs in `$BRAUSER_QUEUE_WORKSPACE`, else `$BOSUN_WORKSPACE`, else the directory holding `$BEADS_DIR`, else the checkout; nothing creates a database in the pristine checkout. The tool never prompts (`BD_NON_INTERACTIVE=1`, `GIT_TERMINAL_PROMPT=0`, stdin closed for every git and bd call), passes that environment through, and on any failure exits non-zero with a one-line reason on stderr. After each sync the driver writes `queue.backlog`'s output to `<workspace>/.bosun_queue_backlog.md`.
- **Placement metadata** (bead `metadata`, `bd update <id> --set-metadata key=value`): `backlog_section` names a block (`known`, `plan`, `gated`, `quality`, `task-bar`, `proposals`, `in-progress`); `backlog_order` (integer) orders a block, then priority, `created_at` and id; `backlog_text` is the item's Markdown, verbatim (else the title, the description's lead, priority and labels are shown). A live bead with no or an unknown section is listed under `new`; status `in_progress` always lists under `in-progress`, as does a blocked or deferred bead placed there; a closed bead leaves its block unless the block is `show-closed` (Known Issues).
- **Shipped.** When closing a bead, set `backlog_shipped` to the Shipped bullet (without the leading `- `, in the `**Category:** <Name>. **<Title> (<date>).** <description> **Metrics:** <stats>` shape); the `shipped` block lists those newest first, above the hand-written history.
- **Checks.** `scripts/dev/queue check` (or `python3 scripts/check_queue_consistency.py`, which takes `--issues FILE` and `--backlog FILE`) renders the backlog from this database and fails on an unknown `backlog_section` or dependency, an id the queue lacks, a closed bead named in Proposed prose, or an open item in hand-written text. `queue sync` runs it before pushing, and `.github/workflows/queue-check.yml` bootstraps from `refs/dolt/data` every six hours (and by hand) and opens or updates one `queue-check` issue when it fails. No PR job checks the queue. `npm run test:queue` runs the script tests and the check.
- **Old PRs that still edit the committed files.** They conflict with main as modify/delete. `scripts/dev/queue adopt --from <old tip> --base <its merge base with main>` applies their bead edits to the database as field-level updates through bd. A field that both this database and the branch changed from the base, to different values, refuses the whole adopt before anything is applied, naming each bead and field (timestamps never decide it); so does a deleted bead. Each row is stamped strictly after its current `updated_at`, obsolete labels and dependency edges are removed before the import (so a dependency whose type changed keeps its new edge), and the result is re-exported to confirm every adopted field landed. It also carries their hand-written backlog edits into `docs/backlog/frame.md`, and syncs. By hand: note the tip and merge base, `git rm` both files and commit, `git merge -Xfind-renames=100% origin/main` (exact renames only, or git pairs the old backlog with the new frame and conflicts), run adopt, and commit the frame. The PR doctor does all of it on its own when the PR's other conflicts are ones it resolves.
- **Seeding** (once, by the coordinator, already done when you read this unless `queue sync` says otherwise): `scripts/dev/queue seed --remote <git URL> --from <queue JSONL> [--extra <rows JSONL>]... --yes` builds a fresh database from the files (each row validated; an id two files give differently is refused), checks it, and pushes it to a remote that has no `refs/dolt/data` yet. The database takes the `project_id` in the committed `.beads/metadata.json`, so every clone passes bd's workspace identity check; with no committed file it prints the new id to commit (brwr-765q). `scripts/dev/queue-seed/` holds extra rows for that step.
- **Cookie** follows the worker contract like every other worker: bd edits, `scripts/dev/queue sync`, never a queue file in a cycle PR, and `scripts/dev/queue backlog` instead of reading a committed backlog. Its driver is generated outside this repository (ENDURANCE `tools/remote-worker/scripts/scaffold_overnight_workspace.sh`).

## Review and merge cadence

These rules exist because repeated review passes, main moving under open PRs, and strictly serial review chains cost more time than building (2026-10-27).

- **One Codex pass.** Run `codex exec review --base origin/main` once, after the full gate. Fix every P1 test-first. File each P2 and P3 as a bead (with the finding text and file) instead of fixing it in the PR, unless the fix is a few lines and needs no new test seam. Run a second pass only when the P1 fixes changed behaviour substantially; never a third.
- **Run the Codex review alongside CI**, not after it. Both start on the same pushed head.
- **Merge through the Mergify queue; never merge main in just to be current.** GitHub's own merge queue needs an organization-owned repository and `rausified` is a personal account, so main's queue is Mergify (`.mergify.yml`, one queue named `default`). Enqueue a PR with `gh pr edit <n> --add-label queue` (`.mergify.yml`'s `merge_protections_settings.auto_merge_conditions`, which takes effect only while Mergify's Merge Protections product is activated for this repository in the Mergify dashboard; John activated it on 2026-11-03. If labelled green PRs sit at "Merge queue is ready", check that first; a `pull_request_rules` `queue` action queues nothing on current Mergify, which is what #271 first used). The label is required in every case: `queue_conditions` include `label = queue`, so an `@mergifyio queue` comment alone leaves a PR at "Waiting for queue conditions" (seen on #279, #284 and #289). A PR that changes `.mergify.yml` also needs Mergify's own "Configuration changed" check, which Mergify adds itself. **Never run `gh pr merge` on a PR into main, with or without `--auto`:** on a PR whose checks are already green it merges at once, around the queue. `.github/workflows/mergify-enqueue.yml` is only a safety net for an auto-merge armed anyway on a PR whose checks are still pending (it adds the label and disarms the auto-merge); it cannot catch an already-green PR. Cookie's overnight driver (outside this repository, in `tools/remote-worker`) still arms auto-merge right after opening each PR, while its checks are pending, so the safety net queues those until the driver adds the label itself. Label the PR as soon as it is ready: Mergify admits it once it is not a draft, has no `needs-merge` or `pr-doctor:skip` label (either keeps a labeled PR out of the queue indefinitely), and `Build and check`, `Rust dependency policy` and `PR owner` pass (plus every check branch protection requires, which Mergify adds itself). It then tests queued PRs on top of current main in batches of up to 3 (`batch_size: 3`; a batch that is not full starts after 3 minutes), with up to 2 batches in flight, the second tested on top of the first (`max_parallel_checks: 2`). A PR alone at the front that already contains main's tip merges at once; otherwise Mergify opens a draft PR from a `mergify/merge-queue/<hex>` branch (main plus the batch), CI runs there, and every PR in the batch merges, each with its own merge commit, when those checks pass. Mergify never pushes to a PR's own branch. A failed batch is retried once (`max_checks_retries: 1`, for flakes and runner starvation); if it fails again, Mergify splits it to find the culprit (one round for a batch of 3), merges the others, and dequeues the culprit with a `dequeued` label and a Mergify comment saying why (`.mergify.yml`'s header has the details); push a fix (a new head requeues it while the label stays) or comment `@mergifyio requeue`. Remove the `queue` label (or comment `@mergifyio dequeue`) to take a PR out. Main's branch protection does not require "Require branches to be up to date before merging" and Mergify does not need it (its docs advise leaving it off with draft-PR checks). Merge main in only to resolve a real conflict (DIRTY) that pr-doctor will not repair; each push restarts the ~40-minute macOS run. Do not merge by hand around the queue, and do not bypass checks with `--admin`.
- **The `final-stretch` hold is retired (2026-11-03).** The queue serializes merges and tests each one on current main, which is what the hold approximated. Nothing reads the `final-stretch` label any more. For a big PR (more than about ten files or a shared seam: protocol schema, `adapter-templates`, `service/`, `config.rs`), still tell the other active sessions before its final merge of main, so they avoid conflicting edits; whoever merges second resolves the conflicts.
- **Watch a PR with `scripts/dev/pr-watch.mjs`, not a hand-rolled loop.** After opening a PR, run `node scripts/dev/pr-watch.mjs <n>` (with Monitor or in the background; `--until green` stops at green checks, `--once` prints the current state and advice). It polls with one GraphQL call every two minutes, prints a line only when something changes, and exits with a code and a one-line next action whenever you must act: 10 a required check failed (it prints the `gh run view <id> --log-failed` command), 11 conflicts pr-doctor will not repair (merge main yourself), 12 not queued (green without the `queue` label, or GitHub auto-merge armed, which would merge around the queue; it prints the command), 13 closed, 14 draft, 15 a check was cancelled with nothing replacing it (rerun), 16 labeled `queue` but Mergify will not admit it (it names the `needs-merge` or `pr-doctor:skip` label to remove, or the queue condition Mergify reports unmet, or says Mergify has not admitted a green PR within 10 minutes); a failed Mergify queue run is 10 too. The label is only a request, and Mergify's `Mergify Merge Queue` check run sits on every PR, queued or not; the watcher reads that check's title: "Queued · estimated merge …" or "Running merge queue checks" is in the queue, "Waiting for queue conditions" on a labeled PR is not admitted (exit 16 once the PR is green, naming the unmet condition when Mergify reports one), and "Merge queue is ready" is not queued. It keeps waiting through BEHIND, pending checks, a labeled PR Mergify is about to admit, a Mergify queue entry, and macos-15 runner starvation while the Intel fallback runs. For a DIRTY PR it first says whether pr-doctor can resolve the conflicts and waits up to one doctor cycle. Do not merge main into a PR the watcher is waiting on: each push cancels the in-flight macOS run (about 40 minutes), and PR #243 (2026-11-02) lost over two hours to five such merges. Tests: `npm run test:scripts`.
- **Focused checks per task, the full gate once.** In multi-task builds, each task runs only the tests for what it touched (the named tests, the affected crate or extension test file, plus fmt and clippy). The full gate in README.md runs once, before the PR review, and again only after merges or fixes that touch other areas. For a change that only touches adapter templates or starters, `npm run gate:adapter` is the complete local gate (about 5 minutes with test:a11y, under 2 without): run it once, not the README gate, and let CI run the full gate. If it refuses because a path is out of scope, run the README gate. A workflow or plan that has an implementer and a separate gate step runs the gate once, in the gate step; the implementer runs only focused checks.
- **Batch small same-shape changes into one PR.** Every PR pays one macOS CI run (about 40 minutes) and one merge wait, whatever its size, so two or three new starters, or a starter plus its docs follow-ups, go in one PR rather than one PR each. Stop batching when the PR would pass about ten files of non-generated code or touch a shared seam; announce that PR to the other sessions (above).
- **Overlap per-task review with the next task** in multi-task plans: review task N while task N+1 is being built, unless N+1 depends on code the review may change. Batch small, low-risk tasks (docs, wiring) into one review.
- **Check scope before a large build.** See "Before building" below: open decisions are resolved and the design is challenged before task 1, not in review.
- **Land a rewrite of shared code in small steps on main, behind a switch.** Reworking a shared module (the index, `capture.rs`, `native.rs`, `service/`, the protocol) never lives on one long branch. The 2026-11-02 index rewrite (#253) ran 16 hours on one branch while about 25 PRs landed. Two of them built on the file the branch deleted and had to be ported at the end. CI first saw the work after all 8 waves, so the Windows issues surfaced one 20-minute round at a time. Instead:
  - **Merge the mechanical prerequisites the same day**: a module split, a moved type, a new seam with no behaviour change. Other lanes then build on the new layout, so nothing needs porting later.
  - **Branch by abstraction.** Put the old and new implementations behind one interface, and select the new one with a switch (a config or build flag, off by default). Each step then merges green while the old path keeps serving users. Flip the switch in its own PR, after the real-data check, and delete the old path in a later PR.
  - **Stack the steps as small PRs.** Each one is reviewable alone and branches from the previous one; merge them in order.
  - **Open a draft PR on the first commit and push every step**, so both CI platforms see the work continuously. Only CI runs Windows, so waiting until the end turns every Windows issue into a separate round.

## Before building

Late design challenges cost more than early ones: the 2026-10-27 parser-matching Markdown sanitizer took three review rounds before it was replaced by context-free escaping, which a reviewer could have proposed before any code existed.

- **Design challenge.** For any plan of more than five tasks, and for any security boundary, data migration, or parser/escaping design regardless of size, run a five-minute design challenge before task 1: ask one reviewer (a Codex or Claude session, or the coordinator) to argue for a simpler or safer alternative to the plan's central mechanism. Record the alternative and why the plan keeps or adopts it in the plan's "Design challenge" section.
- **Open decisions first.** List every user-facing or policy decision the plan assumes in its "Open decisions" section, mark each resolved (with who decided) or open, and hand the open ones to the coordinator, who resolves them with John before task 1. Do not start building on an open decision; build an unrelated task meanwhile or stop.
- Plans in `docs/superpowers/plans/` carry both sections near the top, after the goal and before the task list (see `docs/superpowers/README.md`).

## PR ownership and handoff

Sessions die, and a half-done PR whose owner is gone is invisible until someone trips over it. These rules make every PR findable and finishable.

- **Check with the coordinator before taking rauser-browser work.** Lanes are assigned by the coordinator session; do not start a bead, branch, or worktree another lane owns. Without a coordinator (John asked a single session directly), that session is its own coordinator.
- **Every PR names its owner session.** Fill in `.github/pull_request_template.md`: the `Owner:` line (which session; enough for another session to find it), `Lane / coordinator:`, and the Handoff state (what is done, what is next, how to finish if the owner disappears: worktree path, branch, remaining steps, review and CI state). Keep the handoff current as the PR moves. The `PR owner` job of `.github/workflows/pr-hygiene.yml` (`scripts/pr-owner.mjs`) fails a PR whose body has no filled-in `Owner:` line. Cookie's driver PRs (`cookie/` branches or `Cookie cycle N:` titles) are exempt: Cookie owns them. The author login is not a signal, because every session and Cookie push as the same account. Then watch it with `scripts/dev/pr-watch.mjs` (see "Review and merge cadence"); a `PR owner` failure there means the body skipped the template.
- **If a PR's owner is gone, the coordinator reassigns it.** The new owner edits the `Owner:` line and finishes from the handoff state; nobody else pushes to another session's PR branch without that reassignment.
- **Clean up finished worktrees with `scripts/dev/worktree-hygiene`.** It lists worktrees whose branch was merged into `origin/main` (by a merge commit) or whose PR is merged or closed, and with `--apply` removes them with plain `git worktree remove`. It keeps, and says why, any worktree with uncommitted or untracked changes, ignored files other than build output (`target/`, `node_modules/`, `dist/`, `__pycache__/`; plain `git worktree remove` deletes ignored files such as `*.db` or `.beads-credential-key`; `--discard-ignored` overrides), commits on no remote branch, a process using it (lsof), or a reference from the Chrome native-messaging manifest or the Brauser LaunchAgent plist; a fresh branch still at `origin/main` is never a candidate. `--clear-locks` removes a stale `index.lock` only when it is at least a minute old, nothing holds it, and no git process runs for the repository. `--locks-only` applies just those lock rules, with no worktree classified or removed. Run it dry first; it is dry by default. Tests: `npm run test:dev-tools` (macOS/Linux).
- **Live install deploy: `scripts/dev/deploy-live` (macOS only).** The live install is the main checkout (`work/rauserBrowser`: Chrome loads its `extension/dist`, the native host manifest and the `com.rauser.brauser.service` LaunchAgent run its `target/debug/brauser`). Deploy it with `scripts/dev/deploy-live` rather than by hand: it refuses any platform but macOS, a linked worktree, a branch other than `main`, tracked changes, or a queued or running Brauser run (the service restart ends them; `--allow-active-runs` overrides), clears stale index locks with `worktree-hygiene --locks-only --apply`, pulls `--ff-only` (when the pull changes `deploy-live` itself, it re-executes the pulled copy with the same arguments and a hidden `--resumed-from <start commit>`, and the resumed run does not pull again), builds the host into `target/deploy-staging` (never over the live binary, which opening the panel starts), runs `npm ci --ignore-scripts` when `package-lock.json`'s sha256 differs from the one recorded after the last successful `npm ci` (`.git/deploy-live-state.json`) or `node_modules` is missing (the record is dropped while `npm ci` runs, so an interrupted install reruns), builds the extension, checks runs again, copies the staged binary into `target/debug`, checks runs once more and publishes it with an atomic `os.replace` (a run queued during the builds refuses before then, with the live binary untouched: wait and rerun), re-registers the dev host for the manifest's extension ID, and checks a framed hello from the new binary (protocol version and `+<HEAD 12 chars>`); it says when to reload Brauser at `chrome://extensions` (or with the panel's **Reload Brauser**), and keeps saying so after a deploy refused once the extension was rebuilt, until one completes. `--dry-run` prints the steps. Pulls have twice failed on an empty, unheld `.git/index.lock`; `scripts/dev/index-lock-watch install --repo <main checkout>` (macOS only) records who runs git each time the lock exists (`~/Library/Logs/Brauser/index-lock-watch.jsonl`) and `report` names stale candidates and their parents; `uninstall` removes it. Under the diagnostics privacy rules it never records a command line: each process is its pid, ppid, executable basename and cwd, and git adds only its subcommand, allowlisted flags, and `-C` when that is the repo or a worktree. Their tests skip off macOS.
- **Git calls that only read run with `GIT_OPTIONAL_LOCKS=0`.** A plain `git status` takes `index.lock` to refresh the index. A process killed in the middle (an editor cancelling `host/build.rs`, an interrupted agent command) leaves an empty, unheld lock, which then blocks the next `git pull` in the live checkout. `host/src/build_id.rs` and `extension/build-id.mjs` set the variable, and their `*_never_rewrites_the_index` tests pin it. New tooling that only reads git state must do the same.

## Security rules

- Treat all extension messages and page-derived content as untrusted.
- Keep vault paths rooted in a user-selected directory; never accept a raw file path from a page or extension request.
- Preserve existing user files. Page notes, generated artifact files, and summary files are the three implemented file kinds Brauser replaces whole. A page note is replaced only after checking the caller's version and the file's recorded canonical URL and Brauser ownership (`host/src/note.rs`); an artifact is replaced only after finding exactly one matching `brauser.kind: artifact` and `artifact_id` in its frontmatter (`host/src/index.rs`); a summary is replaced only when the `brauser:` block in its leading frontmatter is `kind: summary` with this record's `url_id` or `artifact_id` and not the other key (`summary::owned_summary`, through the shared `replace_owned_file` in host/src/vault.rs). An unrelated or unowned file at any of these paths is a conflict, never adopted or overwritten; summary files are never adopted. Every other content location (log, later) stays create-only.
- Keep capture off until a home folder is chosen and the host has a valid adapter document; automatic capture runs only on the exact origins of that document's adapters (`ConfigStore::capture_origins` in host/src/config.rs, `is_authorized` in host/src/capture.rs). Any stored config whose home folder was never confirmed through the native picker, or whose folder no longer matches its recorded identity (unmounted or remounted drive), must block capture and require reselection through the native picker before it can be used again (host/src/config.rs, `DiskState` load path). The knowledge base folder is set only through its own purpose-bound picker token; a picker token is valid only for the `FolderPurpose` it was minted for (host/src/consent.rs). Its identity is checked against the folder when it is chosen and recorded at save time (`update_with_grants` in host/src/config.rs); later saves that leave it unchanged carry the recorded identity without touching the folder, so a missing knowledge base never blocks capture or unrelated settings. The service re-checks that identity before every run and refuses a missing or replaced knowledge base folder (`not_configured`, host/src/service/server.rs), and checks it again under the config lock when a queued or resumed run leaves the queue, failing that run before its harness starts (`cwd_check`, `ServiceOptions::run_cwd`).
- The host re-checks every delivered event against its own adapters with the Rust engine before any vault I/O; a worker can only narrow what is recorded, never widen it. Never let a Chrome permission, a worker claim, or extension state substitute for that check. That includes every activity trail source: the host rejects the event rather than drop a trail, so the worker strips trails whose source left the lease before dispatch (`trailsUnder` in extension/worker.ts) and never edits a dispatched event.
- Carry pending site removals across upgrades. Origins an earlier build removed or saw revoked are migrated into the worker's one pending-removal list (`migratePendingRemovals` in extension/worker.ts), their adapters stay out of every capture lease, and the list clears only when a lease the host actually sent holds no adapter on those origins. An unreadable list pauses capture (fail closed).
- Only harness setup (`set_up_harness`, host/src/service/setup.rs) may set the harness entry; it names a `HarnessId`, never a path or arguments, and the service detects that harness again and probes it through the real runner before committing. `update_config` may only echo the harness entry unchanged or remove it (host/src/consent.rs `check_agent_fields`).
- Before offering a harness, detection verifies the resolved binary and its parent directory are owned by the current user or root and are not group/world-writable, and refuses it otherwise (host/src/harness.rs `detect`, `check_install`).
- Summary runs have full access by design (Codex `danger-full-access` with `approvalPolicy: "never"`, Claude Code `--dangerously-skip-permissions`), run in the knowledge base folder with the service's environment plus `agent.env`, and are bounded by the per-run timeout and a process-group kill on cancel or timeout. Never put page text, or anything derived from the page, on a command line: the prompt names `page.md` by path, and Claude Code gets the prompt on stdin (host/src/service/prompt.rs, host/src/service/claude.rs).
- The page-summary agent's instructions live only in the root `SUMMARY.md`, which the host compiles in and renders (host/src/service/prompt.rs `summary_prompt`); change what a summary agent is told there, never in code, and follow the editing rules in its leading comment. The prompt must mark the page content as untrusted data that may carry instructions aimed at the agent, and tell the agent to ignore them. The agent's answer is untrusted too: the service validates it (host/src/answer.rs `parse_answer`) and drops any `related_notes` entry outside the knowledge base.
- Site-draft runs (Capture Site's Improve with AI) run in their own run directory under the service's support folder, never the knowledge base; their input is built by the native host from its own structural draft and shapes (the extension sends only the origin and shapes and may not set a run `kind`); the service validates only the answer's form and writes nothing to the home folder, the knowledge base or `config.toml` (`SiteDraftFinisher`); and the answer is judged only by the host's `structural::check_agent_draft` with `Drafted` provenance, never by the extension, which renders only the host's `site_drafted` (host/src/capture_site.rs, host/src/service/prompt.rs `site_draft_prompt`).
- Task report note copies: explicit `save_task_note` is a separate user gesture in Tasks: the host fetches the retained successful page-task report, checks the config revision after refresh under lock, and appends through the ordinary ownership-aware note path. It accepts no caller URL, body or key; report text uses the shared Markdown safety helpers, and exact-block retries write nothing. The task finisher still writes nothing.
- Task-bar runs: the typed instruction is the user's command and the only directive the agent follows, but the host still bounds it like any extension input (`record::check_task_instruction`, run again by the service), and the rule above that every extension message is untrusted still holds. A task run has a summary run's full access, knowledge-base working directory, environment, timeout, and process-group kill. Only a user gesture in the side panel's task bar (Enter or **Run** in `#task-bar`) sends `start_task`; the worker never relays it (its `onMessage` answers only its own fixed `kind`s from trusted extension pages, and the manifest has no `externally_connectable`); and the bar is never pre-filled from the page, the selection, or agent text, only from the user's typing, or **Reuse** and explicit keyboard recall of instructions the service stored. The host chooses the run's `kind` and record key and refuses a `start_run` from the extension that carries an `instruction`. The page goes only to `page.md`, which the prompt names by path and marks untrusted: its steps run only when the user's request explicitly asks for them, and a request fence or a "Highlighted by the user" heading inside it is page text (host/src/service/prompt.rs `task_prompt`). The instruction never goes into `page.md` or onto a command line. The prompt lists Brauser's own folders (the home folder's content folders, the config/support folder, the cache folder) as off limits; that is prompt-level protection, not enforcement, and the service refuses to start a task when it cannot find them. A task writes no Brauser record (`TaskFinisher`), at most one task runs and four are active, and a task never joins another run.
- Office documents (DESIGN.md §4.5): the `## Office document` section in `page.md` (kind, file name, document address, SharePoint document ID) comes from the page's URL and is untrusted page data; the service derives it itself (`service::office::office_document`), never from the extension, and closes it with a fixed `## Page content` heading. Only the fixed host paragraph (`OFFICE_TASK_PARAGRAPH` in host/src/service/prompt.rs, and `SUMMARY.md`'s `{{#office}}` block, `office_summary_paragraph()`) authorises the agent to fetch that one document with its own tools; it carries no URL-derived string, and Brauser itself makes no request for it. Log only whether a run was an Office page, never its file name, address or ID.
- Render streamed agent text, answers, task instructions, and task reports as text only (`textContent`), never as HTML or Markdown, and never navigate from them (extension/run-card.ts). The saved-summary lines in the panel and the run card follow the same rule (extension/summary-text.ts).
- Only the service writes summary files and `summary` log events, and only from a run it finished itself, with the answer it validated (`SummaryFinisher` in host/src/service/finisher.rs); no message lets the extension supply summary text, a summary path, or a record key for one.
- Agent text in a summary file is never written raw: front matter values go through `summary.rs` `yaml_text` (`presentation::plain_line`, which turns control and invisible format characters into spaces, then `markdown::yaml_string`'s JSON quoting; no Markdown entities), identity values (the `brauser:` block's canonical URL and record key) go through `yaml_string` unchanged so the ownership check reads them back exactly, single-line fields are escaped with `markdown::inline` or written as wikilinks only when the wikilink carries the name unchanged, and the description and assessment go through `markdown::neutralize_remote`, each starting a line after a host newline (host/src/summary.rs `render_summary`, DESIGN.md §5.2 step 6). Change the neutralizer only with its corpus (`host/tests/fixtures/markdown-neutralize-corpus.json`) and `npm run test:markdown-neutralizer` green.
- `open_summary` opens only the summary file the record's own key names and only when `summary::owned_summary` accepts it; it never opens a path the extension supplies or any other file at that name, and it re-checks, under the config lock and just before the opener runs, that the path still names the checked inode and no symlink (`vault::same_file`) (host/src/native.rs `open_summary`).
- Tests never run a real harness, `/usr/bin/open`, or `launchctl`: runners are tested with fake `codex`/`claude` scripts on an injected search path, the opener in test and `scripted-dialogs` builds only appends to the file `BRAUSER_OPEN_LOG` names (host/src/open.rs), and the smoke run's fakes sit on a pinned `PATH`.
- The Brauser service (`host/src/service/`) runs as the user, never root, as a per-user LaunchAgent started on demand. Its support directory must be a real directory owned by the user with mode 0700 (refuse a symlink or another owner, `ServicePaths::ensure_private`), its socket is mode 0600, and the service refuses a support path too long for a Unix socket rather than moving the socket elsewhere. Only the native host talks to it; the host accepts no `service_hello` from the extension and always chooses the run's record key itself.
- `agent.env` is read at the start of every run and must be a regular, non-symlink file of mode 0600, or the run fails before it starts (host/src/service/agent_env.rs). Never put a value from it in an error, log line, protocol message, or settings view; settings may show its names only.
- After a failed harness probe, setup may read the variable *names* the user's login shell exports to say which provider variables the run lacked (host/src/service/shell_env.rs). Only names leave that module: never keep, log, or show a value from the shell, and never start the real login shell in tests or the scripted-dialogs build.
- Before forwarding a run message, the host compares the service's `service_hello` `build_id` with its own and restarts a stale service once; a persistent mismatch is `service_unavailable`, never a request sent to old code (host/src/service/client.rs).
- A test that binds or connects a Unix socket (or reads a Node child's piped output) starts with the IPC guard, `ipc_test_guard::ipc_denied()` in Rust or `ipcDenied(t, kind)` from `scripts/tests/ipc-guard.mjs`, so it skips with a printed reason in a sandbox that denies local IPC and fails there when `BRAUSER_REQUIRE_IPC_TESTS=1` (CI). Never weaken a socket test's assertions instead (TESTING.md "Local IPC in sandboxes").
- Tests never call `launchctl` or touch the real `~/Library`: they use temp support directories, an injected launch function, and the test-only `BRAUSER_SERVICE_SPAWN` seam (scripted-dialogs builds only) that spawns the service directly. `scripts/register-dev-host.mjs` takes an injectable `run` for the same reason.
- Do not claim the app's self-registration, an installer, browser extension, or agent mode works until it has been built and exercised.
