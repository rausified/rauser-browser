## 2026-11-09 — Block known-real identifiers with a salted-hash denylist

Change: Add an optional local pre-commit hook and a CI step that tokenize changed text (host labels, path segments, query values, IDs of 10 or more characters, Jira-style keys, quoted titles) and compare each token's salted hash against a committed denylist, `scripts/denylist.sha256`. The file stores only `sha256(salt + lowercase(token))` lines plus the salt; it never holds a plain value, so committing it leaks nothing. A maintainer adds an entry with `scripts/dev/deny-token "<value>"`, which prints the hash line. Separately, an opt-in local mode (`--evidence <path>`) scans the whole tree against a private evidence file kept outside the repo, for the cases a fixed denylist cannot know in advance. Report file and line plus the token class only, never the matching value.

Why: The repository is public and its rule is synthetic data only, yet real organization, tenant, colleague and board identifiers reached main through ordinary test fixtures and plan examples (a GitHub org slug, a SharePoint tenant and personal-site path, a document GUID, Miro board and widget IDs, board titles). Each looked like a plausible example when written. Review did not catch them because a reviewer cannot tell `acme-corp` from a real slug without private knowledge. A hash denylist lets CI enforce what only the owner knows, and the evidence scan finds new identifiers before they are listed.

Where: `scripts/check_identifiers.py` (new), `.github/workflows/ci.yml`, an optional `.githooks/pre-commit`, and `TESTING.md`. Exempt vendor product text (for example a vendor's own page title such as `Example Meetings`) through a small allowlist of plain values, since those are public by definition.
