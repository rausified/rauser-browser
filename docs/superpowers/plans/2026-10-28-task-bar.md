# Task Bar Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The side panel gets a **task bar**: a free-text field near the top of the panel, directly under the page it uses as context. The user types any instruction and presses Enter. Brauser reads the active tab the way Summarize & log does and runs the configured harness (full-access Codex or Claude Code) through the Brauser service, with the user's instruction as the only directive and the page as untrusted reference data. The task gets its own run card with live progress. When the agent finishes, the card reports back with a plain-text report. Brauser itself writes nothing for a task. This realises the free-text row of DESIGN §5.6 (the Omnibar). Slash commands and `[[commands]]` config stay out of scope.

**Architecture:** Nothing new is invented where the summary and site-draft runs already have it.
- **Run kind.** A third run kind, `task`, reuses the whole run machinery: run records, the queue, the timeout and process-group kill, cancel, recovery, retention, `get_run` polling and streaming, and the one-repair-turn loop in `Supervisor::drive`. These things branch on the kind:
  1. the prompt (`task_prompt` beside `summary_prompt` and `site_draft_prompt`), sent with `OutputSchema::Omit`;
  2. the finisher (`TaskFinisher`: any non-empty final text, capped, nothing written);
  3. the queue (a task never joins another run; at most one task runs and at most four are active);
  4. the view (`RunView.instruction` and `RunView.task_report`).
- **Host-built run.** As with `start_site_draft`, the extension sends a dedicated request, `start_task`. The native host bounds it, resolves the record key under the config lock, and forwards an ordinary `start_run` with `kind: task` and `instruction`. These are fields the host sets and refuses from the extension. The rule that the extension never chooses a kind or a record key stays unchanged.
- **Working directory.** A task runs in the knowledge base, as a summary does, behind the same identity check. The prompt names Brauser's own folders as off limits. This is prompt-level protection, not enforcement, and the docs say so.
- **Report back.** The panel polls `get_run` as it does for summaries. The task card switches to **Done** and shows the report. A visually hidden live region announces the result. Task cards do not follow the page URL, so the result shows even after a tab switch. A panel that was closed restores the cards.

**Tech Stack:** Rust (the `brauser` host and `host/src/service`, `brauser-protocol`), the JSON Schema protocol generated by `protocol/generate.py`, the Chrome MV3 extension in TypeScript, the Node test runner, and the headless macOS smoke `scripts/smoke-macos.mjs`.

## Design selection (2026-10-28)

The orchestrator compared three designs. Each was scored 1 to 5 on correctness against the code, security, scope fit and UX.

| Design | Correctness | Security | Scope fit | UX | Notes |
|---|---|---|---|---|---|
| 1. MVP-first: `instruction` on `start_run`, host infers `kind` | 4 | 3 | 5 | 3 | Fewest additions. But a `start_run` from the extension now carries agent input, which blurs the "host builds every run" rule that AGENTS.md states for site drafts. It also uses a shared `MAX_RUNNING`, so two tasks of up to an hour each can starve every summary. And its `key_id(run, key, id)` signature change touches every scheduler caller. |
| **2. Risk-first: `start_task`, task slot cap, shared bounds** | **5** | **5** | **4** | **4** | **Winner.** A dedicated request keeps the kind and key host-chosen. It closes every risk the readers raised: dedup, starvation, the repair prompt that asks for JSON, the `!summary` means site-draft assumption in `view()`, the frame budget, and resume. Each risk has a named test. |
| 3. UX-first: notifications, history, gestures | 4 | 4 | 2 | 5 | Best UX, but it adds a new `notifications` permission, a worker alarm loop that polls the service, a `ListRunsRequest.kind` filter, a manifest command, a context-menu item and history storage. That is too much surface for the first cut of a shared seam that also has an open 43-file PR (#178, merged since as `484cced`). |

**Ideas grafted into Design 2:**
- From 1: reuse `page_markdown` unchanged for `page.md`. Generalise the settings `SETUP_WARNING` instead of adding a second settings warning. Restore task cards through the same `restorable` rule (every active run plus the 5 newest finished in 24 h that were not dismissed). Add no Chrome notifications in this cut.
- From 3:
  - a `<textarea>` where Enter submits and Shift+Enter adds a newline, with IME composition respected;
  - a one-line **hint** under the bar that always says why the bar is disabled, with Open settings when settings is the fix;
  - a context line, "Uses this page: <title>";
  - **Reuse** on terminal cards, which refills the bar with the instruction;
  - the instruction-aware extraction byte budget (later dropped by amendment 12; see decision 25);
  - the harness-neutral settings copy;
  - the line "Changes the agent already made stay" on stop, timeout and restart.
- Rejected from 3 (follow-up beads): Chrome notifications and badge, the worker alarm, Task history, the `ListRunsRequest.kind` filter, the keyboard command and context-menu gesture, instruction recall with ArrowUp, `/` to focus, autofocus.

  - a new `RunKind` value, `task`;

The panel matches that code and exact text (decision 19), and then asks for a host rebuild. Because the extension cleans the instruction before sending (decision 3a), a current host never gives that text for a `start_task` the extension built.

- Tests never run a real harness, `launchctl`, or `/usr/bin/open`. They never touch the real HOME, `work/rauserBrowser` or other worktrees, and never mutate the test process's environment. Service tests use `HarnessRegistry::of(...)` with in-process fake runners. Host tests use `ConfigStore::for_test`, temp dirs and `service::client::fake::FakeService`. The smoke uses its pinned fake `codex`/`claude`.
- Read DESIGN.md §5.7 and `extension/panel.css` before any panel markup change (user rule: read DESIGN.md before any frontend change). Reuse `.inline-field`, `.secondary`, `.compact`, `.visually-hidden`, `.warning` and the `.run-card*` classes. No glass styling: the panel has none.
- Render the instruction, page titles, streamed text and the report with `textContent` only. Never render HTML or Markdown, never linkify, never navigate from agent text.
- Security and privacy invariants, each pinned by a test named in its task:
  - **Host-built run.** The extension never sends `kind`, `record_key`, `cwd`, prompt or schema. `start_run` from the extension refuses `instruction`.
  - **Where a task can start from.** The instruction is the user's command, but the host still bounds it like any extension input (AGENTS.md "Treat all extension messages … as untrusted" stays). Only a user gesture in the side panel (Enter or Run in `#task-bar`) sends `start_task`. The worker never relays it: its `onMessage` listener accepts only its own fixed `kind`s from trusted extension pages, and the manifest has no `externally_connectable`. The bar is never pre-filled from the page, the selection or agent text; Reuse fills it only with the instruction the service stored (the full `get_run` value). Pinned by `the worker never relays start_task` (Task 9) and `the bar is never pre-filled from the page, the selection or agent text` (Task 10).
  - **Trust split.** The instruction appears in the prompt, which goes over stdin (Claude) or JSON-RPC (Codex), and is also kept in these places, which the privacy docs list:
    - `status.json` (`task.instruction`), for the 30-day/200-run retention;
    - Codex's thread history, through the thread name "Brauser: Task: <first 80 characters>" (`thread_name`, `thread/name/set`, decision 14);
    - `stream.txt`, wherever the harness echoes it;
    - the harness's own session store (Codex threads, Claude Code sessions), which Brauser does not prune.

    The page's title, url, content and selection appear only in `page.md`, which the prompt names by path and marks untrusted. The page title never appears in the prompt. The instruction never appears in `page.md` or on any argv.
  - **Nothing written.** A task writes no summary file, no daily-log event, no note and no config (`TaskFinisher::save` is a no-op).
  - **Bounded everywhere.** The instruction is checked by one shared function in the host and again in the service: 1 to 4096 characters, not blank after trimming, and no control character other than `\n` and `\t`.
  - **Diagnostics redaction** (decision 28). The instruction and the report never reach a diagnostic log: not `host.jsonl` or `service.jsonl` (no span or event field on `start_task`, the forwarded `start_run` with `kind: task`, the `run` span, `drive`'s turn and answer events, `TaskFinisher` or `log_save`), not the extension's `diag` ring buffer, and not a refusal text the host or service logs as `error`. A task's log lines carry only what a summary's do (ids, `kind = "task"`, harness, origin, outcome codes, sizes and timings). Pinned by `a_task_run_logs_neither_its_instruction_nor_its_report` (Task 6), `start_task_logs_neither_its_instruction_nor_its_page` (Task 7), `startTask keeps the instruction out of diagnostics` (Task 9) and the smoke's `checkDiagnostics` canary (Task 12).
  - **Frame budget.** Twenty list views fit in 900 KiB, and the largest task `get_run` fits in 900 KiB. The get_run budget is tight: about 768 KiB of escaped stream page, about 30 KiB of base view, and about 48 KiB of task fields (a 16 KiB instruction of four-byte characters, which serde writes raw, plus a 16 KiB report of `"`, escaped to 32 KiB). The test is mandatory.
- Every Rust-touching task also runs Windows clippy. On Windows, `start_task` answers `service_unavailable`, as the other run messages do.
- Line references are avoided in the steps. Anchors are symbol names (`fn drive`, `Scheduler::submit`, `class RunCards`), element ids (`#task-input`) and smoke step names. The line numbers in "Verified starting point" were first read at `ef5b3ca`, rechecked at `484cced` after the rebase, and serve orientation only.
- Review cadence (AGENTS.md): the review of task N overlaps building task N+1, except where a task is marked *depends on the previous review*. Run one `codex exec review --base origin/main` pass after the full gate. Fix every P1 test-first, and file each P2/P3 as a `brwr` bead.

## Decisions (2026-10-28; decided autonomously; John away, approved)

Every decision below was made on 2026-10-28 by the orchestrating agent while John was away. He granted standing approval for this work, and these are not his explicit choices. Each one can be revisited.

1. **Wire shape.** A new extension-to-host request, `start_task`, answered by the existing `RunStarted`. It carries `url`, `title`, `content`, `selection`, `instruction`, `harness` and `requested_at`, and no `kind` or `record_key`. `RunKind` gains `task`. `StartRunRequest` gains an optional `instruction` that only the host sends to the service. `RunView` gains optional `instruction` and `task_report`. Rejected: inferring `kind = task` from an `instruction` on `start_run`, because it lets the extension's ordinary start message carry agent input.
2. **Protocol version.** Stays at 8, with additive changes only, following the SiteDraft, worklog_report and get_site_restore precedents. No existing field changes type.
3. **Instruction bound.** 1 to 4096 characters. It must be non-empty after trimming, and the only control characters allowed are `\n` and `\t`. One shared `record::check_task_instruction` runs in the host and again in the service, and the schema states the same bound. The panel textarea uses `maxlength="4000"`, which leaves headroom for UTF-16 versus code-point counting. The extension constant for it is `TASK_INPUT_MAX_UTF16_UNITS = 4000`, named so it is not confused with the host's 4096-character `MAX_TASK_INSTRUCTION_CHARS`.

   3a. **Extension clean-up before sending** (amendment 2, 2026-10-28, decided autonomously). `startTask` sends `clean(instruction)`: first `wellFormed` (`extension/extract.ts`; a lone surrogate would otherwise make serde reject the whole frame with the same "invalid or unsupported request JSON" text an old host gives), then every control character other than `\n` and `\t` (`\r`, NEL, VT, ESC and the rest of `\p{Cc}`) replaced with a space, then trimmed. The **trimmed, cleaned** text is what is sent and stored, so Reuse shows exactly what the agent got. If the result is empty, nothing is sent. The host still runs `check_task_instruction` as the backstop.
4. **Trust split.** The typed instruction is the only directive. It is fenced in the prompt between `----- BEGIN USER REQUEST -----` and `----- END USER REQUEST -----` lines. The page goes only to `page.md` (via `page_markdown`, unchanged), which the prompt names by path and marks untrusted, and the agent is told never to exfiltrate because the page asks. The page title is not in the prompt. Besides the prompt, the instruction is kept in `status.json` (for the 30-day/200-run retention), in Codex's thread name, in `stream.txt` when the harness echoes it, and in the harness's own session store; the privacy docs (Task 11) list all four.

   4a. **Page steps** (amendment 6, 2026-10-28, decided autonomously). The page itself never authorises anything. The agent may carry out steps written on the page only when the user's own request explicitly asks for them (for example "follow the setup steps on this page"), and then only the steps that request covers. Any other instruction on the page is not followed and is mentioned in the report. Any `BEGIN USER REQUEST`/`END USER REQUEST` fence that appears inside `page.md` is page text, not the user. So is the `## Highlighted by the user` section (decision 30). DESIGN §4.5 documents this (Task 11).
5. **Working directory.** The knowledge base, through the same `locked_knowledge_base` and harness/timeout setup as summaries, and the same identity recheck when the run leaves the queue (the `Inner::run` filter becomes `kind != SiteDraft`). The prompt lists Brauser-owned locations as off limits:

   - Empty text is an error, which triggers the one repair turn.
   - Otherwise it caps the text at 16 KiB on a character boundary and adds "\n… (report shortened; the activity stream above may hold more)" within the cap, then stores `{"report": text}`. The note does not promise the full output, because the stream itself stops at `STREAM_CAP` (4 MiB).
