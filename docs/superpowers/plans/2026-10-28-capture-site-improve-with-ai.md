# Capture Site: Improve with AI (Agent Drafter) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Capture Site review for a site no starter covers gets an **Improve with AI** button. The structural draft (#138, `brwr-t40`) is still always produced first and stays reviewable and savable on its own. One click on Improve with AI runs the user's configured harness (full-access Codex or Claude Code) through the Brauser service, as Summarize & log does. The agent gets the same private shapes, the structural draft and the host's catalog rules, and returns an adapter-templates draft. That draft may refine the structural one, including Tier 0 rules the structural pass missed. The answer is untrusted: the service validates it strictly with one repair turn, then the host holds it to the same per-rule checks (`check_draft_rules`) and the same match preview, and the panel shows it in the same plain-language review, marked `drafter: "agent"`. The save is unchanged: `check_site_draft` plus a revision-checked `update_config`. With no harness set up, Capture Site keeps working, and the button is disabled with the setup hint Summarize uses. This completes `brwr-f45` (DESIGN §12.2 step 7.7).

**Architecture:** Nothing new is invented where #138 or the open-access service already has it.
- **Run kind.** A service run gains a `kind`: `summary` (every existing run, the default) or `site_draft`. A site-draft run reuses the whole run machinery: run records, the FIFO queue with one queued-or-running run per key, the timeout and process-group kill, cancel, recovery, retention, `get_run` polling and streaming, and the one-repair-turn loop in `Supervisor::drive`. Only four things branch on the kind:
  1. the prompt (`site_draft_prompt` beside `summary_prompt`);
  2. the input file (the run's `page.md` slot holds the delimited untrusted-data block);
  3. the answer validator and finisher (`SiteDraftFinisher`: strict JSON, nothing written to the home folder);
  4. the working directory (the run's own directory, never the knowledge base).
- **Host-built input.** The extension never supplies agent input. A new `start_site_draft` request carries only the origin and shapes, as `draft_site` does. The native host re-runs the structural drafter itself and builds the untrusted-data block from its own draft. It then forwards an ordinary `start_run` with `kind: "site_draft"`, a field the host sets and refuses from the extension.
- **Host-judged result.** When the run succeeds, the panel sends `draft_site` again with the additive `run_id`. The host fetches the run's validated tables from the service (`get_run`, whose `RunView` gains a nullable `site_draft`). A new pure crate function, `structural::check_agent_draft`, judges them with `check_draft_rules`, with `Provenance::Drafted`, against the same existing document, recorded contracts and accepted chain as the structural pass. The host builds the same preview rows and returns `site_drafted` with `drafter: "agent"`. The panel renders that response with the existing `renderDraft`, and saves it with the existing commit path.

**Tech Stack:** Rust (`adapter-templates` crate, `brauser` host and `host/src/service`, `brauser-protocol`), JSON Schema protocol generated by `protocol/generate.py`, Chrome MV3 extension in TypeScript, Node test runner, the headless macOS smoke `scripts/smoke-macos.mjs`.

## User-facing decisions this plan assumes

These follow John's binding decisions. The orchestrator confirms the open ones before the build (AGENTS "Check scope before a large build").

1. **Structural first, agent second.** The structural draft always renders first, and **Improve with AI** refines it on demand. The agent never replaces the structural pass, and **Use basic draft** returns to it. This also applies to the recurring-pages hint. DESIGN §5.1 says "the hint's draft uses the agent when one is set up". This plan changes that so the hint drafts structurally and offers the same button (Task 9 updates DESIGN).
2. **One click, then the same confirm.** Improve with AI needs no prompt, no extra choice and no harness picker: it uses the default harness from settings. The result goes through the same review, the same tenant prefill and the same one-click Save.
3. **Same checks, no new trust.** An agent rule is `Drafted`, never `UserWritten`, so every failing check drops it, with no "warn only".
4. **AI rules the user's pages never showed start unchecked.** An agent rule that matches no visited or link shape starts unchecked, with the label "suggested by AI: no page you visited or linked here matches it" (`unchecked_reason: "unseen"`). This is how "Tier 0 rules a structural pass misses" are offered without silently widening capture.
5. **A rejected or failed agent draft keeps the basic draft.** On a timeout, a cancel, an unparseable answer after the repair turn, a forbidden key or no surviving rule, the review keeps showing the structural draft and says in plain words why the AI draft was not used.
6. **Closing the review cancels the run.** Cancel, close, tab switch or navigation sends `cancel_run` for an unfinished site-draft run, because its shapes are discarded. If the panel window closes, the run finishes on its own. A review reopened on the same origin reattaches to it through `start_site_draft`'s `existing: true`.

## Contract decision: where the agent's answer is judged

- **The service** validates only the form of the answer, so its repair turn can fix what an agent gets wrong by accident. `parse_site_draft_answer` requires:
  - one JSON object (a single code fence is stripped, as `parse_answer` does) whose only key is `adapters`;
  - between 1 and 8 adapters, each an object whose `origin` equals the run's origin;
  - at most 16 `match` rules per adapter;
  - every table parsing as an adapter-templates value with the crate's own parser (`serde_json` → `adapter_templates::value::Value`);
  - an answer of at most 64 KiB.

  The error names the field at fault and carries no answer text, as `parse_answer`'s does. It goes back in `repair_prompt`. A second failure fails the run as `invalid_output`, and nothing is shown (DESIGN §5.1: "a draft that does not parse is discarded without being shown").
- **The service does not reject or repair forbidden keys or failing rules.** Those are safety signals, not format slips, and the host must see them as they came. A repair turn that asks the agent to remove `scope` would hide that it tried. They pass the service unchanged and are judged once, by the host.
- **The host** (`draft_site` with `run_id`) is the only judge of safety. It fetches the validated tables and calls `check_agent_draft`, which applies these rules:
  1. **Whole-draft refusals**, before any preview: any table with a forbidden key (`draft_forbidden_key`), a table for another origin, or a table that does not parse (`draft_invalid_rule`) rejects the whole agent draft. The response is a `site_drafted` with no adapters and one `DroppedView` naming the code. The agent ignored the rules, so none of its draft is shown.
  2. **Per-table checks.** Otherwise each table goes through `check_draft_rules` with all-`Drafted` provenance, `existing`, the recorded contracts, and the earlier accepted tables as `accepted`. This is the same loop as `structural::draft_site`, so a failing rule is dropped with the same `DraftErrorCode` as a structural rule.
  3. **Types.** Types are made unique against `taken`, the starters and earlier tables with the structural Name step's numeric suffix. The ID scheme follows the type. An ID scheme that does not equal the type is `draft_invalid_rule`.
  4. **Review fields.** Each surviving rule gets the same `DraftedRule` fields the structural review shows. `visited`/`links` counts come from filling each input shape and matching the rule without scope (`match_rule`), and `example` from the first matching filled shape, or else the rule's own fill. `link_only`, `token_only` and the new `unseen` follow decision 4.
- **The save does not change.** `check_site_draft` re-judges the selection exactly as it does for a structural draft. Provenance stays all-`drafted`, and the drafter is not sent.
