# Starter families, PR A: family source files and generator (no behaviour change)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the seven shipped starter types out of hand-written TypeScript into one JSON source file per family, generated into the extension, with byte-identical starter offers.

**Architecture:** `protocol/starters/<family>.json` is the source of truth. `scripts/generate-starters.mjs` (Node 24, no dependencies) validates the files, freezes ID templates in `protocol/starters/ids.lock.json`, and writes `extension/starter-families.generated.ts` plus the `starter_types` line of `protocol/capture-site/catalog.json`; `--check` fails when an output is stale. `extension/starter-adapters.ts` keeps its exported API (`starterKind`, `starterOffers`, `matchingStarter`, `STARTER_HISTORY` users) but builds offers by looping over the generated families.

**Tech Stack:** TypeScript (extension, `tsc` via `extension/build.mjs`), Node 24.14.0 scripts and `node:test`, JSON.

**Spec:** `docs/superpowers/specs/2026-11-03-starter-families-design.md` (§2 source format, §5 PR A). This plan implements PR A steps 1–2. **Step 3 (host `taken_types` computed) moves to PR C**: PR A adds no starter type, so the catalog line and the host fixture do not change, and PR A touches no host code or shared seam (no `final-stretch`, no macOS CI).

## Design challenge

Simpler alternative: keep TypeScript as the source of truth and generate only the JSON outputs from the built `dist/starter-adapters.js`. Rejected in the spec (§6): Rust tests would need a Node build to see starter data, and a family's samples, status and vectors would stay spread across files. PR A is the cheapest slice that proves the JSON source can reproduce today's offers exactly, so it is worth landing before the UI work in PR B.

## Open decisions

None open. Resolved (John, 2026-11-03, in the spec): JSON files; status records certification method (`"live"` or `"history"`); drafts are offered. Builder's call in this plan: existing offer keys (`jira:<origin>`, `confluence.page:<origin>`, `sharepoint:<origin>`, `miro.board`, `github.pr`, `github.issue`, `github.repo`) are copied verbatim through a per-type `key` template.

## Global Constraints

- Node 24.14.0 for every script and test (`export PATH=~/.nvm/versions/node/v24.14.0/bin:$PATH`); no new npm dependencies.
- Generated files start with `// Generated by scripts/generate-starters.mjs from protocol/starters/*.json. Do not edit.` (TS) and are deterministic: families sorted by file name, keys in the order written in the source.
- ID templates are frozen: a type's `adapter.id` (and `within.id`) must equal its entry in `ids.lock.json`; the lock is append-only.
- `catalog.json`'s `starter_types` order is the legacy order `["jira.issue", "confluence.page", "sharepoint.doc", "github.pr", "github.issue", "github.repo", "miro.board"]`, new types appended later; the generator rewrites only that one line.
- Nothing in `host/`, `adapter-templates/` or `protocol/schema.json` changes in this PR.
- Local gate: `npm run gate:adapter` must accept the diff (extend its allowlist in Task 3); CI runs the full gate.

## Review Focus

1. **A family file with a typo** (unknown key, missing `adapter.id`, a `key` template without `{origin}` where today's key has one): the generator must fail with the file and field named, never write a partial output. Test in Task 1.
2. **Editing an ID template**: `--check` must fail with `id template changed for <type>` even if every output is regenerated. Test in Task 1.
3. **Origins that are not exactly an https origin** (`http:`, a port, a trailing slash, bare `atlassian.net`, uppercase host): `starterKind` must answer exactly what it answers today. Sweep test in Task 2.
4. **GitHub with no organizations**: offers still list three types with `needs_scope: true` and `adapter: null`, as today (`starter-adapters.ts:269,279`). Existing test covers it; keep it unchanged.
5. **A saved SharePoint adapter on the 2026-10-28 rules**: `starterRuleUpdate` must still offer the update, now reading `history` from the family file. Existing `starter-adapters.test.mjs` cases cover it; keep them unchanged.
